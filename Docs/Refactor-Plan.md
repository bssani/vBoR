# 구조 보수 계획 — 메시 우선·설정 가능·팀원이 쓸 수 있게

> 작성 2026-11-01, Claude. 상태: **초안 — 사용자 확인 전**(§6 결정 항목).
> 근거: 사용자 2026-10-28 방향(아래 §1), HANDOFF "mid review 뒤로 미룬 것", 코드 전수 조사(§2).
> 일정: 50% 평가 **2026-11-19·20**. 회사 PC 계층 덤프(`Tools/DumpHierarchy.py`)는 아직 받지 않았다 — §4 R1은 덤프를 본 뒤 명세를 쓴다.

## 1. 목표 (사용자 2026-10-28)

1. 지금 코드는 Claude가 만든 근사 메시에 맞춰져 있어 실제 CAD로 바꾸기 어렵다.
2. 기능을 켜고 끄려면 C++를 고쳐야 한다(예: 시동 → 사이드미러 펼침).
3. 팀원(사용자가 교육할 사람들)이 다른 차량 메시로도 조립할 수 있어야 한다.
4. 시나리오를 DataAsset으로 관리하듯 BP 조립·기능 추가가 쉬워야 한다.

**원칙(이 계획의 판단 기준):**
- **갈아엎지 않는다.** 판정 로직·추적 손실 처리·시험 632개는 그대로 쓴다. 문제는 "숫자로 정하는 자리", "메시에 대한 숨은 가정", "C++에 박힌 연결" 세 종류다(§2).
- **C++는 상태와 판정, BP는 표현과 선택적 연결.** 부품은 이벤트를 내고, 흔한 반응은 체크박스로, 나머지는 BP Event Graph에서 붙인다.
- **조립 도구를 새로 만들지 않는다.** 차는 공간 배치라서 레벨·BP가 조립 도구다. 부품 목록 DataAsset은 만들지 않는다(§5).
- **50% 전에는 회사 차를 올리는 데 막히는 것만(A), 일반화는 뒤에(B).** 11/16부터 동결.

### 2.2 메시에 대한 숨은 가정

| 가정 | 깨지는 경우 | 어디 |
|---|---|---|
| 움직이는 메시는 **칸 하나**(`DoorMesh`·`PartMesh`·`PanelMesh`) | CAD 문은 메시 여러 개(사용자 2026-10-28 "door가 5개 mesh") — 지금은 merge하거나 BP에 따로 붙여야 함 | 모든 부품 |
| hover·잡기 색은 **그 칸의 메시에만** | 나머지 메시에는 색이 안 보임(촉감 대신인 시각 피드백) | `SetOverlayMaterial` 각 부품 |
| 판정(잡는 상자, 미는 면, 끼임)은 **메시 경계 상자** | 굽은·합친 CAD 메시는 경계가 실제 모양보다 큼 | AxisPart GrabBox, HingedPanel 면, PoweredPanel(P5zg로 일부 해결) |
| 메시 피벗은 차 원점 하나(U-09) | Datasmith는 피벗 0,0,0과 자기 피벗 + Location이 섞여 옴(사용자 2026-10-28) | `MeshRestFromRoot` 계산 |
| 잡기 충돌은 Play 때만 결정 | 에디터·show collision에서 실제 판정 모양이 안 보임 | `ConfigureVBoRGrabCollider` |

### 2.3 C++에 박힌 연결

| 연결 | 지금 | 바꿀 방향(R3) |
|---|---|---|
| 시동(전원) → 사이드미러 펼침·접힘 | 미러가 전원 컴포넌트를 찾아 무조건 구독(`VBoRFoldingMirror.cpp:48`) | 미러에 `Follow vehicle power` 체크박스. 끄면 BP가 `Fold`·`Unfold`를 부름 |
| 시동 버튼 = 태그 `Car.StartButton` | 전원 컴포넌트가 태그로 찾음(`VBoRVehiclePowerComponent.cpp:48`) | 그대로 두되 Check setup에 표시(R5) |
| 키 열림·잠금 → 문 | **연결 없음**(Runner가 횟수만 셈 `VBoRScenarioRunner.cpp:842`) | 사용자가 원하면 문에 `Unlock on key` 체크박스(§6 Q4) |
| 다시 시작 → 리프트게이트·받침대·등받이·미러 초기화 | Runner가 클래스별로 찾아 직접 부름(`VBoRScenarioRunner.cpp:526-537`), 리프트게이트는 태그 `Car.Liftgate`만 | 그대로(평가 흐름). 대신 부품마다 `OnReset` 이벤트를 내서 BP 추가 동작이 같이 초기화되게 |
| 부품 상태 이벤트 | 일부만 BP에 노출(문 `OnOpened` 등, 키 `OnUnlockPressed`) | 모든 움직이는 부품에 `OnStateChanged`(열림·닫힘·잡힘·놓임) + BP에서 부를 명령(`Open`·`Close`·`Lock`·`Unlock`) |

## 4. 작업 목록과 순서

각 R은 명세 하나 이상(한 명세 = 한 기능, AGENTS.md). Codex는 한 번에 하나. 크기는 지금까지 명세(P5z~P5zg) 대비.

| **R0** | `P0Buck.E8Persistence` 간헐 실패 수정 | 작음 | 아니오 | 전체 시험이 믿을 만해야 공사 리뷰가 된다 |

## 5. 하지 않는 것

| 하지 않음 | 이유 |
|---|---|
| 부품 목록·조립을 DataAsset으로 | 레벨·BP와 이중 관리. 시나리오는 순서 데이터라 맞고, 차는 공간 배치라 맞지 않는다 |
| 범용 "반응 규칙" 테이블(트리거 → 대상 → 동작 데이터) | 작은 스크립트 언어를 새로 만드는 셈. BP Event Graph가 이미 그 역할 |
| 기존 메시 칸 삭제 | 근사 차·시험 632개가 쓴다. 새 방식은 추가로 넣고, 칸이 비면 새 방식 |
| 한 명세에 여러 부품 공사 | P0-c 토큰 사례. 부품 종류 하나씩 |
