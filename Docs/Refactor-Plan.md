# 구조 보수 계획 — 메시 우선·설정 가능·팀원이 쓸 수 있게

> 작성 2026-11-01, Claude. 상태: **초안 — 사용자 확인 전**(§6 결정 항목).
> 근거: 사용자 2026-10-28 방향(아래 §1), HANDOFF "mid review 뒤로 미룬 것", 코드 전수 조사(§2).
> 일정: 50% 평가 **2026-11-19·20**. 회사 PC 계층 덤프(`Tools/DumpHierarchy.py`)는 아직 받지 않았다 — §4 R1은 덤프를 본 뒤 명세를 쓴다.

## 1. 목표 (사용자 2026-10-28)

1. 지금 코드는 Claude가 만든 근사 메시에 맞춰져 있어 실제 CAD로 바꾸기 어렵다.
2. 기능을 켜고 끄려면 C++를 고쳐야 한다(예: 시동 → 사이드미러 펼침).
3. 팀원(사용자가 교육할 사람들)이 다른 차량 메시로도 조립할 수 있어야 한다.
4. 시나리오를 DataAsset으로 관리하듯 BP 조립·기능 추가가 쉬워야 한다.

**원칙(이 계획의 판단 기준):**
- **갈아엎지 않는다.** 판정 로직·추적 손실 처리·시험 632개는 그대로 쓴다. 문제는 "숫자로 정하는 자리", "메시에 대한 숨은 가정", "C++에 박힌 연결" 세 종류다(§2).
- **C++는 상태와 판정, BP는 표현과 선택적 연결.** 부품은 이벤트를 내고, 흔한 반응은 체크박스로, 나머지는 BP Event Graph에서 붙인다.
- **조립 도구를 새로 만들지 않는다.** 차는 공간 배치라서 레벨·BP가 조립 도구다. 부품 목록 DataAsset은 만들지 않는다(§5).
- **50% 전에는 회사 차를 올리는 데 막히는 것만(A), 일반화는 뒤에(B).** 11/16부터 동결.

| 가정 | 깨지는 경우 | 어디 |

### 2.4a CAD 작업 흐름 (사용자 2026-11-01) — 모든 차량의 시작점

1. 원본 `.jt`를 Datasmith로 import → §2.4의 Actor 계층(**어떤 차든 여기서 시작**).
2. 그대로는 무거워 쓰기 어려워 **메시를 merge**한다.
3. merge한 메시에 맞춰 **피벗 작업을 손으로** 한다.

→ 공사 목표를 **3단계(손 피벗 작업)를 없애는 것**으로 잡는다. merge는 유지(VR 성능). merge 때 사라지는 CAD 노드 정보(`PIVOT_PIN`, 스위치 노드)는 merge **전에** 표식 Actor로 남기고, 부품 축·버튼은 그 표식에 맞춘다. 판정은 상자로 해서 메시 피벗 위치와 상관없게 한다. 확인 대기: merge 단위, merge 피벗 설정, "피벗 작업"의 정확한 내용(§6 Q6).

## 5. 하지 않는 것

| 하지 않음 | 이유 |
|---|---|
| 부품 목록·조립을 DataAsset으로 | 레벨·BP와 이중 관리. 시나리오는 순서 데이터라 맞고, 차는 공간 배치라 맞지 않는다 |
