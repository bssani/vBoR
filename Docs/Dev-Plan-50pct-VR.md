## 1. 계획 요약

Unreal Engine과 Meta Quest 3로, 참가자가 안내에 따라 차량을 둘러보고 간단히 조작하는 VR 평가 경험을 만든다. Excel의 시나리오 순서대로 진행한 뒤 자유모드로 전환한다. 목표는 정밀한 물리 시뮬레이션이 아니라 **평가할 행동을 이해하고 수행할 수 있는 일관된 경험**이다. 설계 판단에 활용하되, VR에서 확인한 범위를 실제 차량 전체의 사용성 검증으로 확대하지 않는다.

사용자는 시나리오 구현과 프로젝트 개발을 담당한다. 차량 데이터 공급, 음원 녹음, 일정 승인까지 사용자의 단독 책임으로 가정하지 않는다. 이 문서의 독자는 개발 담당자와 준비 내용을 협의할 관계자로 가정하며, 외부 공유는 포함하지 않는다.

> **권장 개발 순서:** 환경·데이터 확인 → 골프백 최소 실험 → 문 밀기 실험 → 안내·공통 입력·시점 전환 → 나머지 항목 통합 → 자유모드·운영 리허설.

문서 작성 기준일은 2026-09-10이다. 사용자와 합의한 요구사항은 아래에 표시했지만, 개발 순서·설계·시험 기준 전체를 승인받은 것은 아니다. 실제 저장소, 엔진 설정, 빌드 및 HMD 실행은 이번 문서 작업에서 확인하지 않았다. 현재 구현 진척은 미확인이다.

- **포함:** VSVA 기반 외관·실내 관찰, 접근·조명, 리프트게이트·짐 적재, 핸들·도어, 승하차·착석, 손가락 도달, 좌석별 시점, 시트 폴딩. Excel 항목별 범위는 다음 절에서 추적한다.

## 3. 참가자 흐름

> 시작 준비 → 현재 번호·행동 안내 → 필요한 위치·대상 표시 → 참가자 행동 → 완료 확인 → 다음 번호 → 마지막 단계 완료 → 자유모드.

예: **03. 외관을 둘러보세요**를 안내하고 경로나 관찰 위치로 유도한다. 도착 이후 표시는 줄여 차량을 가리지 않도록 한다. 경로의 구체적 형태와 음성·문자 사용 여부는 제안 단계다. 특정 결함이나 판단을 유도하는 문구는 피한다.

관찰 단계는 위치에 도착했다는 이유만으로 완료시키지 않는다. 동작 감지와 참가자·진행자 확인을 항목별로 조합하는 방식을 제안한다. 자동 진행 또는 완료 확인 방식은 아직 확정되지 않았다.

자유모드에서는 순서 강제를 해제하고 지원된 관찰·조작을 다시 사용할 수 있게 하는 것을 제안한다. 자유모드는 자유 텔레포트나 안전 제한 해제를 의미하지 않는다. 상태 초기화와 기준 시점 복귀도 제안 기능이다.

## 5. 주요 구현 제안

### 골프백: 가장 먼저 확인할 불확실성

사용자가 처음 구현하는 기능이며 가장 큰 우려 항목이다. 전체 시스템을 먼저 만들기보다 **대표 골프백 한 개, 시작 자세 하나, 적재 위치 하나**로 시험한다.

- **기본안:** 손잡이 부근의 간단한 동작으로 선택하고 손을 따라 이동한다. 회전은 제한하거나 보조하며, 유효 위치 가까이에서만 정렬을 돕는다. 정확한 잡기·놓기 동작은 HMD 시험으로 선택한다.
- **필요한 입력:** 실제 크기를 확인할 수 있는 골프백·박스와 적재 공간 형상, 입구·차체·리프트게이트 간섭 형상. 실제 데이터 제공 여부는 미확인이다.
- **첫 검증:** 최종 위치에 들어맞는지와 입구부터 그 위치까지 이동·회전할 수 있는지를 각각 확인한다. 안착 보조가 차체 관통이나 크기 변경을 숨겨서는 안 된다. 리프트게이트 폐쇄 가능 여부도 별도 확인한다.
- **실패 처리 제안:** 손 추적이 끊기면 이동을 보류한다. 복구 순간 순간이동·던져짐이 발생하지 않도록 기준을 다시 잡는다. 무관한 손 접근으로 선택되지 않아야 한다.
- **단순 대안:** 확인된 경로 위에서 손동작으로 전진·후진한다. 자유 조작 구현은 줄지만 평가 범위도 적재 경로 시연으로 축소된다. 목적 변경을 협의한 뒤 채택한다.
- **재검토 조건:** 보조 적재가 실제 간섭을 숨기거나 잡기·놓기가 반복적으로 실패하면, 자유도를 줄인 대안과 평가 목적을 함께 재검토한다.

> ⚠️ 정적 수납 공간, 입구 통과 가능성, 실제 적재 동작성·신체 부담은 서로 다른 평가다. 보조 적재만으로 무게·힘·마찰을 포함한 실차 적재성을 검증했다고 보고하지 않는다.

### 문: 참가자가 미는 행동을 받아주기

사용자는 유사 프로젝트에서 참가자가 열린 문을 손으로 밀려 했다고 보고했다. 이를 근거로 단순 버튼식 개폐보다 손의 미는 움직임에 반응하는 방식을 먼저 시험한다.

- **기본안:** 문 표면 근처에서 시작된 의도적인 손 이동을 경첩 회전으로 변환하고 허용 각도 안에서 움직인다. 손 전체를 물리 충돌로 처리하는 방식은 첫 실험에서 제외한다.
- **첫 검증:** 밀기, 중간에 멈추기, 손 떼기, 무관하게 지나가기, 추적 손실·재개를 각각 확인한다. 문이 튀거나 저절로 진행하지 않아야 한다.
- **제약:** 실제 저항이 없어 손이 가상 문을 통과할 수 있다. 밀기 시험의 성공을 잡기·당기기까지 지원된 것으로 확대하지 않는다. 개방 조작은 별도로 확인한다.
- **단순 대안:** 큰 동작을 감지해 정해진 개폐 애니메이션을 재생한다. 구현은 단순하지만 손을 멈췄을 때 문도 멈추리라는 기대와 다르다.
- **재검토 조건:** 손 추종이 불안정하거나 오작동을 줄이지 못하면 애니메이션 대안을 시험하고, 사용자에게 조작 근사의 한계를 명확히 한다.

### 공통 입력·진행 구조

초기 구조는 **손 또는 키보드 입력 → 동일한 기능 명령 → 차량 상태 변경 → 단계 완료 판정**으로 나눈다. 엔진 클래스명·플러그인 API는 환경 확인 후 정하며, 범용 프레임워크부터 만들지 않는다.

- 같은 기능을 손과 키보드가 중복 실행해 상태가 뒤집히지 않도록 한다. 좌석 전환 중 추가 전환 입력도 정리한다.
- 진행자 대리 조작과 참가자의 독립 수행을 구분한다. 자동 기록 시스템은 만들지 않으며 초기 시험에는 간단한 수동 기록으로 충분하다.
- 손 추적 손실은 완료가 아니라 보류 사유다. 다시 인식될 때 누적된 손 이동을 한 번에 적용하지 않는다.
- 단계 완료는 사용자 행동과 평가 목적에 따라 판정한다. 관찰, 도달 여부 확인, 문 상태 변경에 하나의 판정 규칙을 강제하지 않는다.
- 기준 시점 복귀·초기화는 운영 보조 제안이다. 키보드 입력을 전달하는 경로는 PCVR 또는 독립 실행 선택 후 확인한다.

### 착수 전 확인할 세 묶음

1. **환경·재사용:** 실제 UE 프로젝트와 버전, PCVR/독립 실행, 사용 중인 손 추적 구성과 구현 진척, 기존 기능의 재사용 범위. 다른 프로젝트와의 관계를 추정하지 않는다.
2. **평가 의미·범위:** 단계 완료 방식, 도달 판정 기준, 문·골프백 보조 방식의 허용 수준, 16번 관찰 시점, Glare·NVH 포함 여부. 데이터·음원 공급 역할도 분리한다.
3. **일정·운영:** 공식 평가일과 Freeze 기간, 평가용 데이터·SW/Cal. 기준, 공간 정렬 검증 및 진행자 키보드 전달 경로.
