## 1. 계획 요약

Unreal Engine과 Meta Quest 3로, 참가자가 안내에 따라 차량을 둘러보고 간단히 조작하는 VR 평가 경험을 만든다. Excel의 시나리오 순서대로 진행한 뒤 자유모드로 전환한다. 목표는 정밀한 물리 시뮬레이션이 아니라 **평가할 행동을 이해하고 수행할 수 있는 일관된 경험**이다. 설계 판단에 활용하되, VR에서 확인한 범위를 실제 차량 전체의 사용성 검증으로 확대하지 않는다.

사용자는 시나리오 구현과 프로젝트 개발을 담당한다. 차량 데이터 공급, 음원 녹음, 일정 승인까지 사용자의 단독 책임으로 가정하지 않는다. 이 문서의 독자는 개발 담당자와 준비 내용을 협의할 관계자로 가정하며, 외부 공유는 포함하지 않는다.

> **권장 개발 순서:** 환경·데이터 확인 → 골프백 최소 실험 → 문 밀기 실험 → 안내·공통 입력·시점 전환 → 나머지 항목 통합 → 자유모드·운영 리허설.

문서 작성 기준일은 2026-09-10이다. 사용자와 합의한 요구사항은 아래에 표시했지만, 개발 순서·설계·시험 기준 전체를 승인받은 것은 아니다. 실제 저장소, 엔진 설정, 빌드 및 HMD 실행은 이번 문서 작업에서 확인하지 않았다. 현재 구현 진척은 미확인이다.

### 포함과 보류

- **포함:** VSVA 기반 외관·실내 관찰, 접근·조명, 리프트게이트·짐 적재, 핸들·도어, 승하차·착석, 손가락 도달, 좌석별 시점, 시트 폴딩. Excel 항목별 범위는 다음 절에서 추적한다.
- **범위 확인:** Glare는 Excel의 추가 데모인 Screen Review로 남긴다. NVH의 도어·리프트게이트·시동 음원은 50% 적용 여부와 제공 범위를 먼저 확정한다.
- **보류:** 65% 확장 기능, 전체 MR 전환 및 VR/MR 이중 모드. 실제 공간 확인용 제한적 패스스루도 현재 확정 기능은 아니다.
- **이번 목표 아님:** 힘·무게·마찰·촉감의 정밀 재현, 자유로운 손가락 물리 시뮬레이션, 자동 평가 보고서·대시보드.

예: **03. 외관을 둘러보세요**를 안내하고 경로나 관찰 위치로 유도한다. 도착 이후 표시는 줄여 차량을 가리지 않도록 한다. 경로의 구체적 형태와 음성·문자 사용 여부는 제안 단계다. 특정 결함이나 판단을 유도하는 문구는 피한다.

관찰 단계는 위치에 도착했다는 이유만으로 완료시키지 않는다. 동작 감지와 참가자·진행자 확인을 항목별로 조합하는 방식을 제안한다. 자동 진행 또는 완료 확인 방식은 아직 확정되지 않았다.

자유모드에서는 순서 강제를 해제하고 지원된 관찰·조작을 다시 사용할 수 있게 하는 것을 제안한다. 자유모드는 자유 텔레포트나 안전 제한 해제를 의미하지 않는다. 상태 초기화와 기준 시점 복귀도 제안 기능이다.

> **사용자 결정(2026-10-16):** 20번을 마치면 자동으로, 또는 진행자 키로 바로 자유모드에 들어간다. 자유모드에서는 참가자도 좌석 버튼(운전석·동승석·2열)으로 고정 시점을 바꾼다(진행자 키도 그대로). 자유모드가 끝나면 진행자 키로 레벨을 다시 연다 — 문·부품·키가 모두 처음 상태가 되고, 저장된 Buck 정렬로 운전석 기준 자리에서 01번부터 시작한다(부품마다 되돌리는 기능은 만들지 않음). 자유모드 전용 실내 부품은 순차 안내 중에도 늘 켜 둔다. 명세는 P5g.
>
> **사용자 결정(2026-10-16) — 관전·진행자:** 평가를 TV로 관전하므로, TV(데스크톱 창)에 참가자 시야 + 아래 띠를 보인다. 띠는 영어로 지금 미션·진행 막대·자유모드·조작 중인 부품 이름을 보이고, 헤드셋에는 나오지 않는다(P5h). 진행자는 따로 뜨는 영어 버튼 창으로 같은 명령을 누르고 상태를 본다. 키보드 단축키도 그대로 쓴다(P5i — 키 이름 일부는 아래 3차 결정에서 바꿈).
>
> **사용자 결정(2026-10-16, 2차) — 정렬 다시 적용·창 디자인:** 진행 중 정렬이 틀어지면 진행자가 **설치 때 저장한 값으로 다시 적용**한다(A 키·버튼 — 키는 3차 결정). 참가자 머리 기준으로 다시 맞추지 않는다(U-07). 지그에서 다시 저장은 P0-c 레벨에서만 한다. 평가는 에디터 VR Preview로 진행하고, 진행자 창은 Play 때 자동으로 뜨며 Play 툴바 아이콘으로 다시 앞으로 가져온다(P5j). 진행자 창과 TV 띠는 같은 어두운 블루 톤(사용자 디자인 시스템 CX Toolkit, 엔진 Roboto)이다.
>
> **사용자 결정(2026-10-16, 3차) — 키·TV 배치:** F1·F5는 엔진 개발 빌드의 디버그 키와 겹치므로 쓰지 않고 알파벳 키로 바꾼다. 처음부터 **R**(F5 대신), VR 안 진행자 정보 **I**(F1 대신), 정렬 다시 적용 **A**(F7 대신). F1·F5 연결은 없앤다. 나머지 키(Space·←·→·O·End·F6·Home·1·2)는 그대로다(P5i). TV는 화면을 꽉 채운다 — 참가자 시야(4:3)를 화면 높이 전체로 두고, 정보는 아래 띠 대신 남는 오른쪽 칸에 둔다. 시야를 가리지 않는다(P5k, P5h의 아래 띠를 바꿈).
>
> **사용자 결정(2026-10-17) — 바깥 바닥 안내:** 바깥 이동 구간의 바닥 안내는 **A안**이다 — 레벨에 그린 스플라인 경로를 따라 진행 방향 V 화살표가 앞으로 차례로 밝아지고, 끝에 노란 도착 고리가 있다. 지금 단계의 경로만 보이고, 고리에 도착하면 꺼진다. 경로는 플레이 영역 밖으로 그리지 않고 차체 자리를 지나지 않는다. 차 안 단계에는 바닥 안내가 없다(P3b). 음성 안내는 여전히 정하지 않았다.

## 5. 주요 구현 제안

### 골프백: 가장 먼저 확인할 불확실성

> **U-10(2026-10-14): 05의 짐은 박스로 바뀌었다.** 아래는 P1 때 기록이다. 같은 구현(손을 따라 이동, Yaw·기울기 제한, 두 손, 안착 보조)을 박스에 쓴다. P1 구현은 놓으면 물리가 아니라 일정 속도로 수직 낙하한다(`VBoRCarryObject.cpp`). 키의 물리 낙하(아래)와 다르다.

사용자가 처음 구현하는 기능이며 가장 큰 우려 항목이다. 전체 시스템을 먼저 만들기보다 **대표 골프백 한 개, 시작 자세 하나, 적재 위치 하나**로 시험한다.

- **기본안:** 손잡이 부근의 간단한 동작으로 선택하고 손을 따라 이동한다. 회전은 제한하거나 보조하며, 유효 위치 가까이에서만 정렬을 돕는다. 정확한 잡기·놓기 동작은 HMD 시험으로 선택한다.
- **필요한 입력:** 실제 크기를 확인할 수 있는 골프백·박스와 적재 공간 형상, 입구·차체·리프트게이트 간섭 형상. 실제 데이터 제공 여부는 미확인이다.
- **첫 검증:** 최종 위치에 들어맞는지와 입구부터 그 위치까지 이동·회전할 수 있는지를 각각 확인한다. 안착 보조가 차체 관통이나 크기 변경을 숨겨서는 안 된다. 리프트게이트 폐쇄 가능 여부도 별도 확인한다.
- **실패 처리 제안:** 손 추적이 끊기면 이동을 보류한다. 복구 순간 순간이동·던져짐이 발생하지 않도록 기준을 다시 잡는다. 무관한 손 접근으로 선택되지 않아야 한다.
- **단순 대안:** 확인된 경로 위에서 손동작으로 전진·후진한다. 자유 조작 구현은 줄지만 평가 범위도 적재 경로 시연으로 축소된다. 목적 변경을 협의한 뒤 채택한다.
- **재검토 조건:** 보조 적재가 실제 간섭을 숨기거나 잡기·놓기가 반복적으로 실패하면, 자유도를 줄인 대안과 평가 목적을 함께 재검토한다.

> ⚠️ 정적 수납 공간, 입구 통과 가능성, 실제 적재 동작성·신체 부담은 서로 다른 평가다. 보조 적재만으로 무게·힘·마찰을 포함한 실차 적재성을 검증했다고 보고하지 않는다.

### 키·미니 테이블·웰컴 라이트 (U-10)

01·02를 접근 거리 대신 키로 한다. 참가자는 차 앞에서 차를 바라보고 시작한다. 세부는 명세 `Docs/Specs/P4a-key-table.md`.

- **배치:** 미니 테이블과 키를 차 앞·차 뒤에 하나씩 둔다(키 두 개, 기능 같음). 형상은 근사이고, 자리는 프로퍼티(자리값)로 둔다.
- **이벤트만:** 키는 "열림 눌림"·"잠금 눌림" 이벤트만 낸다. 웰컴 라이트(앞·뒤 등)와 켬·끔 상태는 사용자가 만든다. 근사 차가 두 키의 이벤트를 모아 다시 내보낸다.
- **쥐기:** 테이블 위 키를 손으로 집는다. 키만 예외로 **자유 6DoF**다 — 손을 그대로 따라 돈다. 정렬 판정은 없다. 다른 손이 잡으면 그 손으로 넘어간다.
- **버튼:** 둘이다(열림·잠금). 키를 쥔 동안, **쥐지 않은 손**의 poke만 받는다. 집으려 뻗는 손이 스치거나 쥔 손가락이 덮어 눌리는 것을 막는다.
  - ISDK poke가 움직이는 키에서 잘 되는지는 아직 모른다. 첫 VR에서 확인한다.
- **놓기·던지기:** 놓으면 물리를 켜서 떨어진다. 손 속도를 이어받아 던질 수 있다(키만 예외).
  - 던질 속도는 추적된 프레임으로만 낸다. 놓기 직전 표본 구간에 추적 손실·Low 프레임이 있으면 속도 0으로 그냥 떨어뜨린다(§5 "던지기" 제외 이유를 키에서 지키는 방법).
  - 추적 손실로 잡기가 끝나면 키는 보류하지 않고 떨어진다. 테이블로 돌아오므로 다시 집으면 된다. 다른 부품의 "손실은 보류" 규칙은 그대로다.
- **되돌리기:** 바닥에 닿으면 같은 키가 자기 테이블 위로 돌아간다. 새로 만들지 않아 사용자가 묶은 이벤트가 유지된다. 바닥보다 높은 곳(차 위 등)에 멈추면 그대로 둔다.

### 문: 참가자가 미는 행동을 받아주기

사용자는 유사 프로젝트에서 참가자가 열린 문을 손으로 밀려 했다고 보고했다. 이를 근거로 단순 버튼식 개폐보다 손의 미는 움직임에 반응하는 방식을 먼저 시험한다.

- **개폐 모델 (U-05):** 문은 닫힌 상태로 시작하며 이때는 밀어도 당겨도 움직이지 않는다. 손잡이를 조작해야 풀리고, 풀린 뒤에는 밀기·당기기를 둘 다 받는다. 다시 닫히면 잠긴다. 단계별로는 08 밖에서 손잡이 해제 후 당겨 열기, 11 안에서 당겨 닫기, 18 안에서 손잡이 해제 후 밀어 열기, 20 밖에서 밀어 닫기가 자연스러운 동작이다. 재잠금 조건과, 손잡이를 잡은 손이 다시 잡지 않고 그대로 문을 당기게 할지는 P2에서 정한다.
- **기본안:** 문 표면 근처에서 시작된 의도적인 손 이동을 경첩 회전으로 변환하고 허용 각도 안에서 움직인다. 손 전체를 물리 충돌로 처리하는 방식은 첫 실험에서 제외한다.
- **첫 검증:** 밀기, 중간에 멈추기, 손 떼기, 무관하게 지나가기, 추적 손실·재개를 각각 확인한다. 문이 튀거나 저절로 진행하지 않아야 한다.
- **제약:** 실제 저항이 없어 손이 가상 문을 통과할 수 있다. 밀기 시험의 성공을 잡기·당기기까지 지원된 것으로 확대하지 않는다. 개방 조작은 별도로 확인한다.
- **단순 대안:** 큰 동작을 감지해 정해진 개폐 애니메이션을 재생한다. 구현은 단순하지만 손을 멈췄을 때 문도 멈추리라는 기대와 다르다.
- **재검토 조건:** 손 추종이 불안정하거나 오작동을 줄이지 못하면 애니메이션 대안을 시험하고, 사용자에게 조작 근사의 한계를 명확히 한다.

### 공통 입력·진행 구조

초기 구조는 **손 또는 키보드 입력 → 동일한 기능 명령 → 차량 상태 변경 → 단계 완료 판정**으로 나눈다. 엔진 클래스명·플러그인 API는 환경 확인 후 정하며, 범용 프레임워크부터 만들지 않는다.

- 같은 기능을 손과 키보드가 중복 실행해 상태가 뒤집히지 않도록 한다. 좌석 전환 중 추가 전환 입력도 정리한다.
- 진행자 대리 조작과 참가자의 독립 수행을 구분한다. 자동 기록 시스템은 만들지 않으며 초기 시험에는 간단한 수동 기록으로 충분하다.
- 손 추적 손실은 완료가 아니라 보류 사유다. 다시 인식될 때 누적된 손 이동을 한 번에 적용하지 않는다.
- 단계 완료는 사용자 행동과 평가 목적에 따라 판정한다. 관찰, 도달 여부 확인, 문 상태 변경에 하나의 판정 규칙을 강제하지 않는다.
- 기준 시점 복귀·초기화는 운영 보조 제안이다. 키보드 입력을 전달하는 경로는 PCVR 또는 독립 실행 선택 후 확인한다.

#### 몰린 버튼 선택 (U-04)

원칙: **도달은 참가자가, 조준은 시스템이 돕는다.** 평가 대상이 찾기·읽기·도달성이므로 조준 보조는 평가를 훼손하지 않는다.

- 손가락 끝에서 **가장 가까운 버튼 하나만** 활성화한다. 여러 개가 동시에 활성되지 않는다.
- 활성 대상이 바뀌는 경계에 **히스테리시스**를 둔다. 손이 미세하게 떨릴 때 대상이 번갈아 바뀌지 않아야 한다.
- 활성 상태를 시각으로 알린다. 촉감이 없으므로 **이것이 접촉을 대신한다.**
- 확정은 poke 또는 pinch로 한다. pinch 확정은 정확한 깊이까지 손을 밀어넣지 않아도 되므로 깊이 판단 부담이 없다. 어느 쪽이 참가자에게 자연스러운지는 P0에서 확인한다.
- **판정 영역은 보이는 크기보다 크게 잡아도 된다. 다만 보이는 크기는 실제 버튼 그대로 둔다.** 라벨 판독·시인성은 평가 대상이므로 시각적 크기·간격을 바꾸지 않는다.
- **레이 포인팅과 머리 방향 조준은 계속 쓰지 않는다.** 손을 뻗지 않고 선택하게 되면 도달성 평가가 사라진다. Quest 3에는 아이 트래킹이 없어 시선 조준은 애초에 불가능하다.
- **13번은 예외다. 판정 영역을 실제 버튼 크기로 둔다.** 그 항목은 도달 자체가 측정 대상이므로 영역을 키우면 도달·미도달 판정이 왜곡된다.

> ⚠️ 오조작 빈도와 버튼 간격 적정성은 이 방식으로 평가할 수 없다. 선택 보조가 오선택을 줄이고, VR에는 촉감이 없어 오조작이 실차와 다르게 나온다. 보고할 때 이 두 항목을 결과로 제시하지 않는다.

> ⚠️ **VR이므로 실물은 좌석뿐이고 나머지는 허공이다.** 실물 콘솔·대시보드·짐이 없으니 손이 실물에 가려지는 일은 없고, 대신 손이 가상 형상을 그대로 통과한다. 조작 설계의 실제 제약은 가림이 아니라 **촉감 부재와 깊이 판단**이다: 참가자는 가상 노브·버튼·손잡이에 닿았는지 스스로 알 수 없으므로 시각·청각 피드백이 접촉을 대신해야 한다. 광학 트래킹에서 남는 가림은 자기 가림, 헤드셋 시야 밖(무릎 근처·좌석 옆·등 뒤), 실물 좌석에 의한 가림이다. 손가락 끝 위치로 각도를 산출하는 방식(노브 등)은 지터와 깊이 판단에 취약하므로 P0·P1에서 실제로 확인한 뒤 채택 여부를 정한다.

> ⚠️ 조작 신호(손가락별 pinch, pinch 강도, 마이크로제스처)는 현재 포함된 Meta XR 플러그인만으로 Enhanced Input에서 바로 얻을 수 있다. 반면 hover·select 상태 판정, 잡기 후보 선택, 1축 제약 변환, 추적 손실·복구 처리, 관통 방지 시각 보조는 **인터랙션 레이어**가 필요하다. 이 레이어를 직접 만드는 것은 "범용 프레임워크부터 만들지 않는다"에 어긋나므로, 검증된 인터랙션 플러그인으로 **ISDK 1.205.0을 포함했다 (U-05).** 쓸 클래스와 쓰지 않을 클래스는 조사 기록 §4를 따른다. 단 ISDK의 잡기는 추적 신뢰도를 보지 않으므로 추적 손실·복구 처리는 직접 얹어야 한다 (조사 기록 2026-10 §2).

### 착수 전 확인할 세 묶음

1. **환경·재사용:** 실제 UE 프로젝트와 버전, PCVR/독립 실행, 사용 중인 손 추적 구성과 구현 진척, 기존 기능의 재사용 범위. 다른 프로젝트와의 관계를 추정하지 않는다.
2. **평가 의미·범위:** 단계 완료 방식, 도달 판정 기준, 문·골프백 보조 방식의 허용 수준, 16번 관찰 시점, Glare·NVH 포함 여부. 데이터·음원 공급 역할도 분리한다.
3. **일정·운영:** 공식 평가일과 Freeze 기간, 평가용 데이터·SW/Cal. 기준, 공간 정렬 검증 및 진행자 키보드 전달 경로.
